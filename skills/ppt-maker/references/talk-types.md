# 발표 유형별 구성

구성의 출발점이다. 청중과 목적에 맞게 줄이거나 바꾼다. 연구 발표 예시는 RVLAB 실제 발표 네 편(저장소에 포함하지 않는 로컬 `templates/examples/`)에서 확인한 구성이다. 어떤 밀도와 표현이 어울리는지는 템플릿의 DESIGN.md가 더 구체적으로 말해 준다.

## 뼈대

목차는 섹션(`#`)이 Chapter, 토픽(`##`)이 그 아래 항목이 된다. 시간은 슬라이드당 약 1분에서 시작해 조정한다.

| 유형 | 섹션 순서 | 마지막에 둘 것 |
| --- | --- | --- |
| 진행 보고 | 지난 피드백·이번 목표 → 한 일과 설정 → 결과(비교 기준·조건) → 문제와 원인 가설 → 다음 계획 | 받고 싶은 판단이나 질문 |
| 논문 리뷰 | 문제와 동기 → 핵심 아이디어 → 방법 구성요소 → 실험 설정·결과 → 한계와 우리 연구와의 연결 | 적용할 점과 열린 질문 |
| 스터디·튜토리얼 | 왜 필요한가 → 개념·원리 → 핵심 코드와 실행 결과 → 정리 | 다음 범위. 긴 코드·추가 예제는 `# Appendix`. 혼자 따라 하는 A-Z 실습은 [ppt-tutorial](../../ppt-tutorial/SKILL.md) |
| 학회·디펜스 | 문제 → 기여 → 방법 → 실험·결과 → 한계·향후 과제 | 기여 요약 |
| 제안·경영 보고 | 결론·요청 → 근거 → 옵션 비교 → 위험·비용·일정 | 결정 사항. 세부 근거는 `# Appendix` |
| 제품·기술 소개 | 문제 → 해결 → 데모·사례 → 동작 원리 → 다음 단계 | 행동 요청 |

여러 논문이나 기법을 다루면 각각을 섹션으로 두고 같은 토픽 이름으로 여러 장을 이어 쓴다. 이전 발표를 잇는 발표는 첫 섹션에 지난 내용 요약을 한 장 둔다.

## 좋은 슬라이드의 조건

- 상단 바는 토픽 이름, `###`는 청중이 기억할 결론이다. 질문형이면 본문 첫 줄에서 바로 답한다.
- 핵심 문장은 가능하면 한 줄로 쓴다. 그림 그리드(그림 2~4개) 슬라이드에서는 두 줄째가 그림 공간을 줄인다.
- 문단 대신 근거 몇 개를 불릿으로 쓰고 설명은 `::: notes`로 옮긴다. 긴 문단 슬라이드는 발표장에서 읽히지 않는다.
- 결과에는 비교 기준·조건·표본 수·단위를 함께 적는다. 학습 지표와 실제 평가 결과를 섞지 않는다.
- 논문 그림·표에는 `::: source`로 저자·연도·링크를 단다. 전체 서지는 노트에 둔다.
- 코드는 핵심 부분만 코드 블록으로 쓰고 실행 결과를 옆이나 다음 장에 붙인다.

## 연구자에게 그림 요청

1. 기획 단계에서 `plan/outline.md`의 `figure`에 표현·근거·재사용/생성 여부를 적는다.
2. `slides.md`에 `![짧은 캡션](figures/이름.png "요청 내용")`으로 자리를 잡는다. 파일 이름은 내용을 드러내는 영문 소문자·하이픈으로 정한다.
3. `uv run pptgen lint tasks/<task>`의 `missing_figures` 목록을 전달한다. 빌드는 그 자리에 점선 요청 상자를 그린다.
4. 초안 PPT의 그림을 재사용할 수 있으면 `figures/draft/`로 꺼낸 파일을 제안한다.

좋은 요청은 그림 하나가 핵심 문장 하나를 증명하게 한다. 예: "제안 방법이 BC보다 성공률이 높다" → `x: 조건(BC·ACT·제안), y: 성공률(%), 막대 위에 시행 수, sources/eval.csv`.

## 빌드 후 확인

- 표지의 날짜·제목·부제·발표자·소속이 맞다.
- 목차의 Chapter와 섹션, 항목과 상단 바 이름이 일치한다.
- 각 슬라이드가 핵심 문장 하나를 그림·표·불릿으로 뒷받침한다.
- 요청 상자로 남은 그림과 출처 없는 인용을 보고한다.
- 템플릿 DESIGN.md의 "빌드 후 볼 것"을 확인한다.
